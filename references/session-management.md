# 会话、断点与多人协作协议

> SKILL.md §5 的展开。长书写作必然跨几十个会话、可能多人接力，本协议保证任何时刻"关窗不丢工作、换人不丢上下文"。

## 1. 底层原理（为什么能随时关窗）

- 上下文接近上限时系统会做**有损摘要压缩**后继续，丢的是"对话记忆"，不是"项目"——台账、书稿、书目缓存全部在磁盘上。
- 因此只要每批次把该写的文件写了、该登的台账登了，对话窗口本身没有不可再生的信息。
- **资产在磁盘文件里，不在任何对话窗口里。**

## 2. 会话生命周期

### 开工（每个新会话）
1. 读台账 §2 断点 → 读目录与指令清单定位批次 → 查术语台账 → 一句话向作者确认范围。
2. 不重复生成已完成内容；不把旧对话粘贴进来。

### 关窗前收账
1. 确认批次收尾四件事已完成 → 直接关窗（台账已有 ✅ 记录，无损失）。
2. 批次中途必须关窗/被压缩的：①核对最后落盘文件完整；②断点写入台账 §2"进行中"（写到哪个小节、证据清单是否已核、下一步）；③顺手把"已核未登"的题录摘录进台账 §4 缓存。

### 批次内被压缩时
- 在**小节边界**收束：写完当前小节并落盘后收束，不在"证据已检索、正文未落盘"的中间态硬撑续写。
- 压缩后纪律：被压缩掉、未经文件固化的题录**一律视为不可信**，须重新核对原文后方可写入参考文献——宁可重查，不凭记忆写引用。

## 3. 多窗口并行

- 并行前提：两条轨道的批次**不共享章节**（如主线写第三章、副线写第十章），且台账 §2 能区分记录。
- 窗口按"轨道-批次"命名（如 `主线-3.2`、`副线-10.1✅`），防止在错误窗口续写。
- 表/图编号指针在**章内**是排他资源：不同轨道不得写同一章，否则编号必然冲突。
- 已收尾窗口保留最近 1~2 个备查、其余可删（删前核对台账该批次有 ✅）；每完成一章清理一次会话列表。

## 4. 多人接力（交接）

1. 交出方：确保所负责章节全部批次收尾完成（台账 ✅），写一份**交接说明**（工作方法静态快照：任务范围、进度、各章注意事项、已知坑），与工作空间一同移交。
2. 接收方：按"第一天开工路线"——读交接说明 → 通读目录自己负责的部分 → 读台账 §1~§4 → 读术语台账符号表 → 与交出方确认语料权限 → 一句话确认范围开工。
3. 权威顺序不变：台账 > 其他管理文件 > 交接说明快照（快照会过时，台账永远新鲜）。
4. 语料不随文件移交时（如知识库在原持有人的应用内）：按降级方案执行——只用台账 §4 缓存书目，新文献请持有人代查。

## 5. 与作者的交互节奏

- 每批次：开工一句话确认 → 收尾一份汇报（文件清单/脚本结果/遗留 WARN/下批预告）。
- 作者科研特色浓的章节：可按作者要求设"每小节确认门"——小节完成后展示核心论点与证据要点，待作者确认再写下一小节（瓶颈工序，宁慢勿抢）。
- 每章：章末小结完成后的人工检查点（符号一致性、跨章衔接、台账 §5 清零）。
- 台账 §5 的待裁定事项在汇报中主动提请作者裁决，不要积压到不可收拾。
